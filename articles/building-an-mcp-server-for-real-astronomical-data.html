Building an MCP Server
for Real Astronomical Data

Two tools, two computation sources, one protocol: what building a Model Context Protocol server taught me about exposing a real production system to AI agents without exposing its source.

ProtocolMCP, stdio transport
Tools2, different sources
Verified byReal client handshake
Format
First-hand build log
Audience
AI engineers & agent-tooling teams
Focus
MCP servers, structured tool outputs

I kept reading about MCP before I had actually called a tool through it, and that bothered me enough to go build one.

I run Magical Chart, an astrology product with real paying users, sitting on top of an astronomical engine I validated against Swiss Ephemeris reference data across ten bodies. MCP is the open standard for connecting AI agents to external tools, and every explanation of it I had read made sense on paper. What I did not have yet was the feeling of it: what it is actually like to define a tool, have a client discover it, and watch a call go through end to end. The only way I know to get that feeling is to build something and watch it fail a few times first.

So I wrote a small server with two tools, and I made sure the two tools were not just cosmetic variations of each other. One does its own math locally. The other reaches into my own production system and asks it for a real answer. That gap between them turned out to be where most of the actual learning happened.

Two tools, on purpose

get_planet_position is the simple one. It runs entirely on the open-source astronomy-engine library, with a thin astrology layer I wrote on top to map a longitude onto a zodiac sign. No network call, no API key, nothing that can go down. Give it a body and a date, it hands back a position. This tool exists mostly so the server has a baseline: something I can trust completely, to compare against when the other tool starts doing something strange.

get_natal_chart is the one I actually cared about. It calls Magical Chart's own live, public, unauthenticated natal-chart API over HTTP, the same Swiss Ephemeris-validated engine that generates the reports my paying customers read. The tool does not reimplement any of that logic. It makes a real HTTP request, gets back real placements, houses, aspects and chart angles, and hands that straight to whatever agent asked for it. The engine's results are exposed; the engine itself is not.

I went back and forth on whether that second tool was worth the trouble. It would have been faster to ship two local calculations and call it a day. But a server with two identical-shaped tools teaches you how to write a tool schema. It does not teach you what happens when the thing behind your tool is slow, rate-limited, or occasionally just unreachable, which is the actual condition most interesting MCP servers will live in once they wrap something real instead of a toy function.

A production API still needs defensive handling behind the protocol

Because get_natal_chart calls a real endpoint, it inherits that endpoint's real limits. The API is rate-limited server-side, sixty requests a minute for anonymous callers, and I did not want the tool to paper over that by quietly retrying until it either succeeded or looked broken from the outside. So when the limit is hit, the tool says so plainly instead of pretending everything is fine.

Latitude and longitude are optional on the same endpoint, since houses and the ascendant only mean anything with a real birth location. Early on, I just let the tool fall back to coordinates of zero, zero when they were missing, which is technically a valid pair of coordinates and therefore technically a valid, completely wrong answer. I changed that once I noticed it: when the coordinates are missing, the response now carries an explicit notice field saying so, rather than returning houses that look plausible and are not. An agent calling this tool, or a person reading its output later, should not have to guess which numbers are real.

The afternoon lost to a module resolution bug

The bug that actually cost me time had nothing to do with MCP. astronomy-engine's own package.json points its "import" condition at an ESM build, without a nested package.json in that folder marking it "type": "module". Node's resolver follows that pointer, finds a file it cannot parse the way it expects, and fails in a way that does not obviously point back at that mismatch. I spent a while assuming the problem was in my own code before I isolated it down to a single import line.

The fix, once I found it, was almost anticlimactic: use createRequire to pull in the package's CommonJS build directly, since Node's "require" condition resolves correctly where "import" does not. One line, with a comment next to it so I would not have to relearn this the next time I touch the file. It is a small, specific bug, and not one I would have hit by reading documentation about MCP, which is exactly the point: most of what building this taught me was not about the protocol at all.

Verifying against a real handshake, not a syntax check

A tool schema that parses is not proof that the tool works. Before I called this done, I ran the server against a real MCP client: initialize, then tools/list to confirm both tools showed up with the shape I intended, then an actual tools/call against each one, the local calculation and the live API path separately. The local one is easy to get right and easy to trust. The live one is the one where I actually wanted to see, with my own eyes, a request leave my machine, hit magicalchart.com/api/v1/natal, and come back as a structured result the client could read.

That last step is the one I would flag to anyone building an MCP server quickly, including past me a few weeks ago. A client that can see your tool definitions has told you nothing about whether a call against them returns what you expect. Those are two different claims, and only the second one matters to whoever is relying on the tool.

What stuck with me

Decide early where each tool's answer actually comes from, local computation, a cache, a live backend, because that decision quietly shapes everything downstream of it: what can fail, what needs a timeout, what deserves its own error message instead of a generic one. Return structured, schema-validated output rather than a sentence an agent has to parse, since the whole appeal of giving a model a tool is that it gets something it can act on directly. And treat backend limits, rate limiting, missing inputs, partial results, as information worth surfacing, not edge cases worth hiding.

None of that is specific to astronomy. It is just what showed up once I stopped reading about MCP servers and tried running one against something real.

About this project: this is a demo built to learn MCP hands-on, not a repackaging of Magical Chart's production astrology logic. get_natal_chart exposes that engine's live results over its existing public API; it does not expose the engine's source.
