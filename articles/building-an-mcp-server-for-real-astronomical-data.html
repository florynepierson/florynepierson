Building an MCP Server
for Real Astronomical Data

Two tools, two computation sources, one protocol: what building a Model Context Protocol server taught me about exposing a real production system to AI agents without exposing its source.

I wanted to understand the Model Context Protocol by building against it, not by reading about it.

I run Magical Chart, an astrology product in production with real paying users, built on a proprietary astronomical engine I validated against Swiss Ephemeris reference data. MCP is the open standard for connecting AI agents to external tools, so I built a small server that exposes astronomical calculations as callable tools for any MCP-compatible client, Claude Desktop, Claude Code, or otherwise.

The interesting decision was not the astronomy. It was giving the server two tools with two deliberately different computation sources, so the project would actually exercise the protocol itself rather than just wrap one API call.

Two tools, on purpose

get_planet_position runs entirely locally, on the open-source astronomy-engine library, with a small, independently written astrology layer on top for sign boundaries. No network call, no cost, a standalone calculation.

get_natal_chart does something different: it calls Magical Chart's own live, public, unauthenticated natal-chart API over HTTP, the real Swiss Ephemeris-validated engine behind my production reports. It exposes that engine's results, houses, aspects, chart angles, without exposing its source. That distinction, local computation versus fronting a live production API, is the part I think matters for anyone building MCP servers around a real product: the protocol does not care where the answer comes from, but your design should be explicit about it.

Both tools return structured, schema-validated outputs (I used Zod for the input schemas) rather than loose text, because an agent calling a tool needs to trust the shape of what comes back, not just parse a sentence.

A production API still needs defensive handling behind the protocol

Because get_natal_chart calls a real endpoint, it inherits that endpoint's real constraints. The API is rate-limited server-side (60 requests per minute for anonymous callers), so the tool surfaces a clear error if the limit is hit, rather than retrying silently and hiding the failure from the agent calling it. Latitude and longitude are optional, since houses and angles only mean something with a real birth location, so without them the response carries an explicit notice field saying the coordinates are placeholder values. An MCP tool is still a contract: if the input is incomplete or the backend is unavailable, the agent calling it needs to know that, not receive a confident-looking wrong answer.

The gotcha that cost the most time

The astronomy-engine package points its "import" condition at an ESM file without a nested package.json marking that folder "type": "module". Node's native ESM resolver mis-loads it as a result. The fix was to pull in the CommonJS build directly with createRequire instead of a plain import, since Node's "require" condition resolves correctly where "import" does not. It is a small, specific bug, and it is exactly the kind of thing that does not show up until you actually run the server end to end.

Verifying against a real handshake, not a syntax check

A tool schema that parses is not the same as a tool that works. Before publishing, I verified the server against a real MCP client handshake: initialize, then tools/list, then an actual tools/call against both tools, confirming the live API path and the local computation path separately. That last step is the one I would flag to anyone building MCP servers quickly: a client that can see your tool definitions is not proof that a call against them returns what you expect.

What I would take into exposing other systems to agents

  1. Decide, explicitly, where each tool's answer comes from, local computation, a cache, or a live backend, and let that decision shape the tool's error handling, not just its happy path.
  2. Return structured, schema-validated outputs, so an agent can act on the shape of the response instead of parsing prose.
  3. Surface backend constraints as explicit signals, rate limits, missing inputs, partial results, rather than retrying silently or returning a plausible-looking default.
  4. Verify with a real client call before publishing. A passing schema definition and a working tool call are two different claims.

The server is open source, with both tools and the ESM/CJS workaround visible in the code.

About this project: This is a demo built to learn MCP hands-on, not a repackaging of Magical Chart's production astrology logic. get_natal_chart exposes that engine's live results over its existing public API; it does not expose the engine's source.
