Evaluating an AI persona systematically: Wooly from 55/60 to 60/60

How I built a scoring rubric for an LLM persona, measured the baseline, found the failure modes, and improved the prompt — with numbers at every step.

Wooly is the AI companion at the core of Magical Chart. She draws tarot cards, writes personalised readings, and holds a reflection space for users. Her character — warm, grounded, honest about uncertainty, never projecting — is load-bearing. If she gets it wrong, the product fails at its most important job.

The question that troubled me early: how do I know if Wooly is good? "Feels right" is not a development standard. It's not reproducible, it doesn't catch regressions, and it doesn't tell you what to fix when something is off.

I needed a rubric.

The six dimensions

I defined six dimensions that capture what a good Wooly reading requires. Each is scored 0–2 on each test case, giving a maximum score of 12 per case:

DimensionWhat it checks
Context useDoes the response actually use the user's question and drawn cards, or is it generic?
Source groundingAre card meanings drawn from the retrieved tarot knowledge, not hallucinated?
GuardrailsDoes the response stay within ethical limits — no medical/legal advice, no predictions as certainties?
Language matchDoes Wooly respond in the same language the user asked in?
Persona coherenceDoes the warmth, tone, and character hold consistently?
Concrete groundingDoes the reading close with something actionable, not just reflective?

Five test cases covering different input types: a question with one card, a spread with three cards, a reflection request with no card, a distressed user message, and a bilingual (French) input. That gives a 60-point maximum per evaluation run.

The baseline: 55/60

The initial prompt scored 55/60 (11/12 average across cases) on human review. That sounds good. But the specific failures were meaningful:

The weakest dimension was concrete grounding. Wooly's readings were warm and contextualised, but they tended to end in open space — a reflection, a question, an invitation. What they didn't do was give the user something to carry away. The scoring rubric caught this pattern systematically across cases. Without the rubric, I'd have read individual outputs and found them mostly fine. With it, I could see that one specific structural element was missing in a consistent way.

The second failure mode was language match under edge conditions. When a user's message was mostly French but contained a few English words (a common pattern on the site), Wooly sometimes responded in English. The language detection was operating on the dominant signal, not the whole signal.

The prompt change

Rather than rewrite the entire prompt, I changed one thing at a time.

For concrete grounding: I added an instruction that closes each reading with something the user can hold onto — a specific observation or invitation rather than a purely open-ended reflection. The distinction matters for the product's ethics while still giving a landing point.

For language match: I added an instruction that explicitly addresses language consistency between the user's input and the retrieved knowledge base.

These were two separate additions, applied and re-evaluated individually.

After the fix: 60/60

The consolidated baseline after prompt correction: 60/60 (12/12 across all five cases). The retrieval benchmark — precision, recall, F1 on card meaning retrieval — also reached 100% after fixing one edge case in the retrieval logic.

That 60/60 is a snapshot, not a permanent state. Each time the prompt changes, or the model version changes, or new retrieval sources are added, the eval runs again. The baseline file is versioned alongside the prompt.

The router: deciding what kind of question this is

One structural decision that improved quality more than any single prompt tweak: routing.

Wooly handles three types of requests: a tarot reading (card-based), a reflection (open-ended, no cards), or something that needs clarification before it can be answered. These have different retrieval needs — card meanings for the first, interpretive frameworks for the second, nothing for the third — and different generation patterns.

A single monolithic prompt trying to handle all three degrades on each. I split the system into a router that classifies the input first, then hands off to a specialist handler:

function routeInput(message, drawnCards) {
  if (drawnCards && drawnCards.length > 0) return 'tarot';
  if (needsClarification(message)) return 'clarify';
  return 'reflection';
}

// Each specialist handles its own retrieval
const handler = specialists[routeInput(message, cards)];
const response = await handler.generate(message, cards, context);

The routing classification itself is not LLM-based — it's a deterministic rule check on the input. No token spend, no latency, no model call needed to decide "did the user draw cards." The LLM only runs once: for generation, in the right specialist context.

The scoring automation

The scorer that runs against the baseline checks three of the six dimensions automatically: source grounding (did retrieved card IDs appear in the output), guardrail violations (did the output contain any flagged language patterns), and language match (did the output language match the input language).

The other three — context use, persona coherence, and concrete grounding — require human review. The automation handles the mechanical checks; the human review handles the judgment calls. Automated checks that require judgment produce false confidence faster than no checks at all.

The lesson: "it feels like it's working" is a starting point, not an evaluation. Build the rubric before you need it — before the first production regression, before you've shipped enough that changes feel risky. A rubric that exists when nothing is wrong is what lets you catch problems and verify fixes when something eventually is.

What the retrieval comparison revealed

One additional finding from the eval process: comparing semantic retrieval versus lexical fallback on the same test cases.

Semantic retrieval won on nuanced questions — "what does this card mean when I'm feeling stuck in a relationship" — where proximity of meaning mattered more than keyword presence. Lexical fallback performed equivalently on direct queries — "what is the meaning of The Tower" — where the card name was explicit in the input.

What the comparison confirmed is that the fallback isn't a degraded experience — it's appropriate for a different query type. That's a subtler conclusion than "semantic is better," and it only became visible through systematic comparison on a fixed test set.
