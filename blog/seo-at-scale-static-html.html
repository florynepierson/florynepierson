SEO at scale with static HTML: consolidating 264 pages into 22

How I went from ~1,500 thin SEO pages to 22 genuinely rich ones — and why reducing page count was the right move.

The standard SEO playbook for content sites says: more pages, more keywords, more indexed URLs. For a while, Magical Chart followed that playbook. The result was roughly 1,500 pages, hundreds of them near-duplicate: variations on the same zodiac sign, the same tarot card, the same astrological concept with slightly different phrasing in the title.

The crawl budget was spread thin. Pages competed with each other for the same queries. And importantly, none of those thin pages gave a user a reason to stay.

The consolidation changed the architecture: 264 near-duplicate pages merged into 22 genuinely rich ones, with 301 redirects preserving link equity. This is what I learned from doing it at that scale in plain static HTML.

Why static HTML at this scale

No framework. No build step. No SSR. Every page is a file on disk, served directly by Vercel's CDN. This matters for SEO in two ways: pages are crawlable by default (no JavaScript rendering required for content), and load times are as fast as a static file can be.

The tradeoff is that "updating 264 pages" means writing a script that opens 264 files, makes the change, validates the output, and writes it back. There's no CMS, no template re-render, no database update that propagates. Everything is explicit.

That explicitness is also why things like the structural parser for modifying scripts (described in an earlier post) became necessary. When files are the source of truth and you're operating at hundreds or thousands of them, the tooling has to be robust — because there's no abstraction layer to catch mistakes.

Identifying the pages to consolidate

The first step was categorising pages by content uniqueness, not by URL structure. A page about "The Tower tarot card" and a page about "The Tower reversed meaning" might have different URLs but share most of their content. A page about "Capricorn daily reading" and a page about "Capricorn weekly reading" might look distinct but have the same intent: someone who wants to know what astrology says about Capricorn right now.

I grouped pages by semantic cluster — what user intent does this page serve? — and within each cluster, identified which page had the most content, the strongest backlink profile, and the best Search Console performance. That page became the canonical target. Everything else became a 301 source.

The critical check before each consolidation: read the Search Console data for the pages you're about to remove. One page I nearly 301'd had a 6.4% CTR at position 8.9 — six times the site average at that position. It was the strongest page in its cluster. The redirect would have been a mistake. The data was nine days old in an export I had on disk; I had to query live GSC data to catch it.

The 301 redirect implementation

Static HTML on Vercel means redirects live in vercel.json. For 264 source URLs redirecting to 22 targets, the config block is long but mechanical:

{
  "redirects": [
    {
      "source": "/tarot/tower-reversed",
      "destination": "/tarot/tower",
      "permanent": true
    },
    {
      "source": "/tarot/tower-upright",
      "destination": "/tarot/tower",
      "permanent": true
    }
    // ... 260 more entries
  ]
}

I generated this config block from a spreadsheet mapping each source URL to its target, then validated every entry before deploying: each source should return 301, each target should return 200. A script ran the checks automatically — 264 HTTP requests, flagging any that didn't match expectations — before the config went live.

E-E-A-T: adding real identity to thin content

The consolidation was a cleanup operation. The growth came from something different: adding genuine author identity and trust signals to the pages that remained.

Google's E-E-A-T framework (Experience, Expertise, Authoritativeness, Trustworthiness) has become increasingly important for content in sensitive verticals — health, finance, and, as it turns out, astrology and tarot, which Google classifies as "wellness/spirituality." Pages without a named author, without a clear editorial policy, without explanation of how readings are generated, were being treated with skepticism.

I added:

  • An "About this reading" section explaining what Wooly is and how the AI generation works
  • An author byline linked to a real profile page
  • "How it works" pages explaining the methodology behind natal charts and tarot interpretations
  • Explicit editorial disclaimers: readings are for reflection, not prediction

These aren't keyword optimisations. They're trust signals that change how Google weighs the content — and they also changed how users engaged with it. Time on page went up on pages with the "how it works" section. The content gave users something to understand, not just consume.

What the architecture constraint forced

Building SEO at this scale in static HTML forces a discipline that frameworks can obscure: you have to know what every page contains, because there's no dynamic rendering to paper over gaps. When I ran the consolidation audit, I found a significant number of pages with no analytics tag at all — invisible to measurement. I found pages without an .html extension that existed on disk but were never served. I found pages whose canonical URLs didn't match their actual URLs.

None of these were visible at the product level. They only appeared because the static file audit had to be explicit. A framework with a CMS would have handled some of this automatically — but it also would have made it harder to see the raw state of what was actually deployed.

The constraint of "every page is a file, every change is explicit" is slower. It's also more auditable. For a site where SEO is a primary acquisition channel and correctness of metadata is load-bearing, that tradeoff was worth it.

The result

The consolidation didn't immediately spike rankings. 301 redirects take time to process, and Google re-evaluates the target page's authority after absorbing the redirected link equity. What it did immediately was simplify the crawl: fewer URLs, clearer topical focus per remaining page, no self-competition between near-duplicate variants.

The growth that followed came from the combination of consolidation, E-E-A-T additions, and new content in clusters that had no existing coverage. No single change explains it. The consolidation was the foundation that made the other changes land.
