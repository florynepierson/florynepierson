Tech & Engineering

Overlay — ce qui apparaît sur la vidéo
My analytics were broken for 5 days. I had no idea.
Légende
A 2-second setTimeout on 1,536 pages was making most of my traffic invisible to GA4. The tag was there. The script loaded. But it fired before the page was actually ready — so GA4 never registered the visit. I was making product decisions on data that didn't exist. The fix: load the analytics script after the page is interactive, not on a timer. 20 minutes to fix. Weeks to find. If your GA4 numbers feel off, check when your tag actually fires — not just whether it's installed. Save this if you run your own site. 🔖
Overlay
My Stripe webhook was failing 100% of the time. Zero error logs.
Légende
Paying users weren't getting access. The webhook looked configured. Nothing was written to the database. The bug: I was sending the 200 response before verifying the signature. Stripe marks a webhook as successful the moment it gets a 200 — it doesn't care what happens after. So my endpoint was confirming receipt, then failing silently on signature verification. The fix: verify the signature first, then process, then respond. The scariest bugs in production are the ones that don't throw errors. They just quietly don't work. Drop a 🔥 if you've ever debugged something that "looked fine."

50 fake sessions per day. GA4 didn't catch a single one.
Légende
Headless Chrome scrapers running real JavaScript. Real GA4 events. Real session data. GA4's built-in bot filter is based on user-agent strings. These bots had clean user agents. The tell: screen dimensions of exactly 1280×1200 and 1366×1366. No real device has those dimensions. I added a check at the top of every analytics script: if those dimensions match, block all tracking. If you're making conversion decisions from your analytics, you need to know what's actually in your data. Save this. 🔖

I built an entire site in plain HTML. 1,500+ pages. No framework.
Légende
Not because I'm a purist. Because I needed to understand every file on my site. When SEO is your main acquisition channel, you can't afford abstraction you don't control. No build step = every page is crawlable by default. No framework = no JavaScript rendering required for content. No CMS = every change is explicit and auditable. The tradeoff: "updating 300 pages" means writing a script that opens 300 files and validates every one. The constraint became the architecture. And it taught me more about how the web actually works than any framework ever did. What's your stack? 👇
Overlay
I built an astronomy engine precise to 0.003°. It started at 0.29°.
Légende
Two bugs. Both coordinate system errors. Neither threw an exception. Bug 1: I was using an event search function to get the lunar nodes position instead of calculating the actual instantaneous position. 0.29° error. Fixed with a cross-product calculation. Bug 2: I was mixing equatorial and ecliptic coordinates without converting. 1-2° error on some planets. Rule I follow now: measure the broken state first. Use a known reference (I used Swiss Ephemeris). Then fix. Never touch the code before you know what "correct" looks like. Save if you work with precision calculations. 🔖
Overlay
Every serverless function should do exactly one thing.
Légende
Generate a reading. Check a quota. Process a webhook. When a function starts doing two things, debugging becomes a guessing game. When it does three, you've lost track of what it's responsible for. Single responsibility isn't a principle for large teams. It's how one person keeps a production system understandable at 2am when something breaks. My rule: if I can't describe what a function does in one sentence, it does too much. What's the most useful engineering principle you actually apply day-to-day? 👇
Overlay
A project works when you're watching. A product works when you're not.
Légende
The gap between the two is monitoring, error handling, and the edge cases you didn't think of. I learned this after my first deployment where everything worked perfectly — until I closed my laptop. Things that only exist in a "product" and not a "project": → Alerts when something that should happen doesn't → Graceful failure when an external API is down → Logs you can actually read at 11pm on a Sunday Building something that runs without you watching is a different skill than building something that works. Save this if you're moving from projects to real products. 🔖
Overlay
I built a quota system that users can't trivially bypass.
Légende
The naive version: store the count in localStorage. The problem: anyone can open DevTools and clear it in 3 seconds. My approach: two layers, each doing what it's suited for. Layer 1 — localStorage: fast, local, drives the UI. Shows remaining count. Resets at midnight. Not the enforcement layer. Layer 2 — server-side: every reading request checks against the database. If the user clears localStorage, the server still knows. Design principle: client-side state is a display cache, not authoritative truth. Anything you don't want to enforce server-side shouldn't be enforced at all. Save this if you're building a freemium product. 🔖

Growth & Business

Overlay
14x organic traffic in 2 months. Here's what actually moved it.
Légende
Not one thing. Three, in the right order. 1. Consolidation: 264 near-duplicate pages merged into 22 rich ones, with 301 redirects preserving link equity. Fewer pages competing for the same query. 2. E-E-A-T: added a real author byline, "how it works" pages, editorial disclaimers. Google weighs trust signals in sensitive verticals — astrology qualifies. 3. New content in clusters with no existing coverage. The consolidation didn't spike rankings. It simplified the crawl and created the foundation for the other two to land. SEO is rarely one lever. It's usually three done in the right sequence. Save this if you're working on content SEO. 🔖
Overlay
Google sends me the most traffic. Google sends me zero paying users.
Légende
Direct traffic — people who typed the URL or came from a saved link — converts. Google doesn't. Why: the intent arriving from Google is curiosity. Someone searched "free tarot reading" and landed on my site. The intent arriving direct is return — someone who already experienced something and came back for more. Traffic and purchase intent are different things. Optimising for one doesn't optimise for the other. I almost spent months improving pages that rank well but never sell. The data stopped me. Before you optimise for traffic, ask: what's the intent of the people already coming? 👇
Overlay
I picked one channel first. Pinterest. Here's why that was the right call.
Légende
Not because Pinterest is the best channel. Because I could only do one thing well. Each channel has one job: → Pinterest: make people curious about your universe before they know what you sell → Google: capture people who already know what they want → Instagram: build trust through face and voice → X: credibility and builder community Mixing these up without knowing what you're asking each one to do is how you waste all three. You don't diversify until the first channel actually works. What was your first channel? 👇
Overlay
I changed my price 3 times in 4 months. Each time I had a hypothesis.
Légende
Pricing isn't a decision you make once. Each change tested something specific: → Does a lower price increase conversion enough to offset the margin loss? → Does annual pricing convert differently from monthly? → Does geographic pricing change the composition of paying users? The data answered each time. Sometimes yes, sometimes no. The mistake isn't changing your price. It's changing it without knowing what you're measuring. Before you change your price, write down the hypothesis first. Then look at the data after. That order matters. Save this if you're figuring out pricing. 🔖

I sent 189 cold outreach messages. 1 response. Here's what I learned.
Légende
Not 1 conversion. 1 response. Cold outreach without an audience is noise. You're asking for attention from people who have no reason to trust you yet. What I did instead: built in public, documented what I measured, made the work visible. Inbounds are slower to start. They compound. Overlay
Urgency converts. Discount alone doesn't.
Légende
I ran two promos: "50% off" — no end date. Conversion barely moved. "50% off — ends tonight." — meaningfully better. Same discount. The difference was the deadline. Why: a discount without urgency gives the user permission to come back later. And later almost never happens. The other lesson: if a 30% discount doesn't move conversion at all, the problem isn't price. It's desire. No discount fixes a product people don't want enough. Before your next promo, decide: are you testing price sensitivity or desire? They need different experiments. Save this. 🔖

I built a scoring rubric to evaluate my AI persona's personality.
Légende
6 dimensions. 10 points each. 60 points total. → Context use: does it actually use the birth date provided? → Source grounding: does it reference the cards drawn? → Guardrails: does it avoid prediction and dependency? → Language match: does it mirror the user's tone? → Persona coherence: is it consistently Wooly, not generic GPT? → Concrete grounding: does it give something specific to sit with? Baseline: 55/60. After two targeted prompt fixes: 60/60. You can't improve what you don't measure — including personality. The model doesn't have a personality by default. You define it, then you score it. Save this if you're building LLM products. 🔖

I use AI for the first version of every design. Then I refine.
Légende
AI gets you to 80% of a design in an hour. The first version is fast enough to test whether the layout logic is right. Good enough to show to users. The difference between AI as a feature and AI as the product.
Légende
AI as a feature: "we added AI to summarise your notes." AI as the product: the AI is why the product exists at all. When AI is the product, every design decision flows from one question: does this make the AI experience better? Not cheaper. Not faster. Better for the user in front of it. Nobody tells you when you're doing well as a solo founder.
Légende
No manager. No team. No sprint review. No quarterly feedback. You learn to read the data the way other people read feedback. Open rate up → something resonated. Conversion flat → the funnel has a hole. Churn spike → something broke the trust. The data doesn't tell you you're doing well. It tells you what's working and what isn't. That's actually more useful. The hardest part of building alone isn't the technical problems. It's sitting with uncertainty long enough to let the data answer. Solo founders: what's your signal that something is working? 👇

Product

Overlay
My AI never tells you what will happen. That's a product decision.
Légende
Every reading ends with a question, a reflection prompt, something to sit with. Not a prediction. Why: prediction erodes trust. If the AI says "you'll meet someone in June" and June passes, the product broke the user's experience. Reflection builds trust. The user brings their own meaning to the reading and leaves with something that felt true to them — because they made it true. This is also the ethical line. An AI in a sensitive category has to know what it won't do. The model won't draw that line by itself. You have to draw it in the product. What ethical guardrails have you built into your product? 👇
Overlay
The free tier has to be real. Or the paid tier doesn't earn itself.
Légende
Real reading. Real AI. Real output. Every day. No account required. If you need to hide or weaken the free tier to sell the paid one, the paid one isn't good enough yet. The funnel data was clear: users who experienced at least one full reading before seeing a price converted at a significantly higher rate than users who hit a registration wall first. The free experience isn't a cost. It's the acquisition mechanism. The upgrade case should be obvious on its own: "I want more of this" — not "I guess I have to pay to continue." What does your free tier actually give users? 👇

Blockchain & Web3

Overlay
What a smart contract actually does in plain English.
Légende
A smart contract is code that lives on a blockchain and runs automatically when conditions are met. No middleman. No "processing time." No "our team will review." Example: escrow. Normally you need a bank or a lawyer to hold funds until both parties fulfil their obligations. A smart contract does the same thing — but the rules are written in code, visible to everyone, and execute automatically. The interesting part: the code is public, immutable, and runs the same way for everyone. That's what "trustless" actually means — you don't need to trust the other party, you trust the code. The less interesting part: writing that code correctly is extremely hard. Most smart contract bugs are irreversible. Save this if you're new to Web3. 🔖
Overlay
I read a blockchain for the first time as a developer. Here's what I actually saw.
Légende
Not price charts. Not NFT jpegs. A chain of blocks, each containing a list of transactions, each linked to the previous one by its hash. Change anything in block 47 and block 48's hash breaks. And 49. And every block after it. That's what makes it tamper-evident. It's not magic. It's cryptographic linking and distributed consensus. What surprised me: how readable it is. Every transaction is public. You can look up any wallet address and see its entire history. What didn't surprise me: the UX is still terrible for anyone who isn't already technical. That gap between what it can do and how hard it is to use — that's where the interesting products are being built. What's your mental model of blockchain? 👇
Overlay
Web3 UX is broken and everyone in the industry knows it.
Légende
Seed phrases. Gas fees. Wallet addresses. Irreversible transactions. Every one of these is a user experience failure waiting to happen. Seed phrases: 12 random words that if lost mean you lose everything forever. No recovery. No support ticket. Gas fees: you want to send $5 but you need to pay $3 in fees that fluctuate unpredictably. The technical foundation is solid. The UX layer built on top of it is still treating normal users like they're cryptographers. The products that will win in Web3 aren't the ones with the most sophisticated smart contracts. They're the ones that make this usable by someone who's never read a whitepaper. That's an engineering and product problem. Which means it's solvable. What's the worst Web3 UX you've encountered? 👇
Overlay
Decentralisation is a spectrum, not a binary.
Légende
"Is it decentralised?" is usually the wrong question. The right questions: → Who controls the smart contracts? (Can they be upgraded? By whom?) → Who controls the frontend? (If the website goes down, can you still access your funds?) → Who controls the oracles? (External data fed into the contracts) → Who owns the majority of the governance tokens? Most "decentralised" protocols are decentralised on some dimensions and highly centralised on others. That's not necessarily a problem — full decentralisation has real costs in performance, upgradeability, and UX. But understanding where the centralisation actually lives tells you where the real risks are. Save this if you're evaluating Web3 projects. 🔖
